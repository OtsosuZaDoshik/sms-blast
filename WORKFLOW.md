# GitHub Actions: как это работает

Руководство для первого знакомства, на примере этого репозитория.

## Что такое workflow

Workflow — это **инструкция для чужого компьютера**. Вы описываете шаги в
YAML-файле, кладёте его в репозиторий, и GitHub по некоторому событию
поднимает у себя чистую виртуальную машину, выполняет там ваши шаги и гасит
её.

```
событие  →  GitHub поднимает чистую машину  →  шаги по порядку  →  результат
(нажали                (windows-latest)         (установить,        (артефакт
 кнопку)                                         собрать, проверить)  или ошибка)
```

Три вещи, которые важно понять сразу:

1. **Машина каждый раз новая и пустая.** Ничего от прошлого запуска не
   остаётся. Поэтому в шагах прописана и установка Python, и установка
   зависимостей — на вашем компьютере это делается один раз, а там каждый раз.
2. **Ваш компьютер ни при чём.** Можно закрыть ноутбук — сборка продолжится.
3. **Шаги идут по порядку и падают на первой ошибке.** Если шаг вернул код
   не ноль, дальше ничего не выполняется и весь запуск помечается красным.

## Где живёт файл

```
.github/workflows/build-windows.yml
```

Строго в **корне** репозитория. Файл внутри подпапки (например
`build/.github/workflows/`) GitHub просто не увидит — это первая ошибка, на
которую натыкаются все.

## Наш workflow по шагам

```yaml
on:
  workflow_dispatch:        # кнопка «Run workflow» вручную
  push:
    tags: ["v*"]            # ещё и автоматически при теге v1.0 и подобных

jobs:
  windows:
    runs-on: windows-latest # какая машина нужна
    steps:
      - uses: actions/checkout@v4      # скачать код репозитория
      - uses: actions/setup-python@v5  # поставить Python
      - name: Установить зависимости
      - name: Скопировать исходники в src
      - name: Собрать exe                  # PyInstaller
      - name: Проверить, что exe запускается
      - uses: actions/upload-artifact@v4   # отдать файл вам
```

`uses:` — это готовый чужой блок (действие), `run:` — ваши команды. На
Windows-раннере команды в `run:` выполняет PowerShell.

Шаг **«Проверить, что exe запускается»** здесь не для красоты: он запускает
собранный `.exe`, ждёт, пока поднимется панель, и дёргает четыре страницы.
Если хоть одна ответит не `200` — запуск покраснеет. Смысл в том, чтобы вам
никогда не выдали сломанный файл.

## Главная ловушка: ветка по умолчанию

Из документации GitHub:

> To trigger the `workflow_dispatch` event, your workflow must be in the
> default branch.

То есть кнопка **«Run workflow»** появится, только если файл workflow есть в
ветке `main`. Даже если вы хотите собрать код из ветки `desktop`.

Порядок такой:

1. Файл workflow должен попасть в `main` (влить ветку или закоммитить туда).
2. Кнопка появится на вкладке **Actions**.
3. **В самой кнопке выбирается ветка**, из которой брать код. Хотите собрать
   `desktop` — выбираете `desktop` в выпадающем списке.

## Как запустить

### Через сайт

1. Открыть репозиторий → вкладка **Actions**.
2. Слева выбрать workflow — **«Сборка Windows exe»**.
3. Справа кнопка **«Run workflow»** → выбрать ветку → **«Run workflow»**.
4. Через несколько секунд в списке появится новый запуск.

## Как следить за ходом

На сайте: Actions → щёлкнуть по запуску → щёлкнуть по имени задачи слева.
Видно каждый шаг, его можно развернуть и прочитать вывод. Шаги
раскрываются по мере выполнения.

В терминале:

```bash
gh run watch
```

Показывает прогресс прямо в консоли и ждёт завершения. Просто список
последних запусков:

```bash
gh run list --limit 5
```

## Как забрать результат

Собранный файл называется **артефактом**. Он не попадает в репозиторий —
лежит отдельно, привязанный к запуску.

На сайте: открыть запуск, промотать вниз до раздела **Artifacts**, скачать
`smsblast-windows` (придёт zip-архивом, внутри `smsblast.exe`).

В терминале:

```bash
gh run download
```

Скачает артефакты последнего запуска в текущую папку.

**Артефакты хранятся 90 дней**, потом удаляются автоматически. Если сборка
нужна навсегда — делайте релиз (`gh release create v1.0 smsblast.exe`).

## Как читать падение

Красный крестик — значит какой-то шаг вернул ошибку.

1. Открыть запуск, найти шаг с красным значком (он всегда последний
   выполнявшийся).
2. Развернуть его и читать **снизу вверх** — настоящая причина обычно в
   последних строках, выше идёт обычный вывод.
3. Исправить у себя, закоммитить, запустить снова.

Полезно: кнопка **«Re-run jobs»** повторяет запуск без нового коммита —
удобно, когда сбой был случайным (сеть отвалилась при установке пакета).

## Сколько это стоит

Для **публичных** репозиториев Actions бесплатны без ограничения минут. Этот
репозиторий публичный, так что платить не за что. У приватных есть месячная
квота бесплатных минут, причём windows-раннер расходует её быстрее
linux-раннера.

## Частые ловушки новичка

| Симптом | Причина |
|---|---|
| Кнопки «Run workflow» нет | файла workflow нет в ветке по умолчанию (`main`) |
| Workflow вообще не виден | файл не в `.github/workflows/` в корне репозитория |
| `Invalid workflow file` | сломан YAML — почти всегда отступы, они делаются **пробелами**, табы запрещены |
| Пуш отклонён: `without workflow scope` | у токена `gh` нет права на запись workflow-файлов |
| Всё зелёное, а файла нет | забыт шаг `upload-artifact` — сборка прошла, но результат остался на удалённой машине и погиб вместе с ней |
| Шаг «не видит» файл из прошлого шага | шаги делят папку, но не переменные окружения; и `cd` в одном шаге не действует на следующий — для этого есть `working-directory` |

## Ваш текущий блокер

Пуш файла workflow сейчас отклоняется:

```
refusing to allow an OAuth App to create or update workflow ... without `workflow` scope
```

GitHub намеренно требует отдельного разрешения на запись в
`.github/workflows/` — чтобы приложение с доступом к коду не могло втихую
добавить в репозиторий выполняемый скрипт. Выдать разрешение можно одной
командой, она откроет браузер:

```bash
gh auth refresh -h github.com -s workflow
```

После этого файл workflow можно закоммитить и запушить обычным образом.

## Шпаргалка

```bash
gh workflow list                              # какие workflow есть
gh workflow run build-windows.yml --ref main  # запустить
gh run list --limit 5                         # последние запуски
gh run watch                                  # следить за текущим
gh run view --log-failed                      # показать лог упавших шагов
gh run download                               # забрать артефакты
gh run rerun                                  # перезапустить
```
